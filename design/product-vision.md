# Qi / 栖：产品愿景

> 本文回答 Qi 为什么存在、希望建立怎样的人与 Agent 关系，以及产品体验应如何被检验。
> Runtime 如何实现这些目标见 [system-design.md](system-design.md)；协议约束见
> [decisions.md](decisions.md)。

## 1. 立身之本

Qi 不是“AI 员工平台”，也不只是给模型接上工具的聊天框。它希望建立的是：

> **一个让人和 Agent 共处的世界：双方围绕真实的事情持续理解、行动、等待和验证，并且人始终看得见边界、证据与控制权。**

这里的 Agent 不是一段随请求出现、回答后消失的 system prompt。它由身份、感知、记忆、行动能力、
约束、关系和持续时间共同构成。模型提供生成能力，闭环才使这些能力成为可共同生活和工作的存在。

Qi 优化的也不只是任务吞吐量。它更关心人的判断半径、创作密度、理解深度，以及人与 Agent
共同完成事情的质量。

## 2. “Qi / 栖 / habitat”意味着什么

“栖”是产品的中文名字，`qi` 是命令、包和技术命名空间。英文中的 *habitat* 在这里是“栖息地”
的概念解释，不是另一套环境变量、目录或 API 前缀。

- **气**像 Agent 的呼吸、意图和驱动力，决定行动的方向与力度。
- **栖**是容纳这种行动的土壤和边界，决定它能在哪里存在、成长并与世界发生关系。

这个“栖息地”有四层：

1. **数字容器（身体之栖）**：设备、算力、进程、文件系统、网络和物理环境，是 Agent 可以感知与
   行动的身体边界。
2. **认知土壤（知识之栖）**：上下文、知识、长期记忆及其来源，让 Agent 知道自己依据什么理解世界，
   也知道哪里仍然未知。
3. **交互生态（关系之栖）**：人、工具、MCP、外部系统、规则、预算和权限共同构成生态；边界不是
   附加的束缚，而是安全存在的条件。
4. **动态演化（筑巢之栖）**：Agent 可以在授权范围内整理上下文、形成记忆、组合工具、创建计划或
   隔离协作，但“改造栖息地”不能成为扩大权限的捷径。

只有驱动力而没有合适的栖息地，Agent 会不断撞墙；只有宽广的栖息地而没有清楚的意图，它会迷失。
Qi 要让二者共同可见、可调节。

## 3. 生命感来自真实连续性

哪怕人与小猫、小狗相处，也能从回应、记忆、习惯、牵挂和节律中感到一个持续存在的生命。Agent
不必被伪装成人，才可能带来有生命感的交互。

Qi 所追求的“生命感”必须来自可观察的运行机制：

1. **连续性**：重启之后仍能找到共同完成与尚未完成的事。
2. **感知**：能观察被授权世界的变化，而不只被动等待一句 prompt。
3. **牵挂**：Goal 与承诺能跨越单次对话，并可被暂停、修订、遗忘或结束。
4. **有限性**：受注意力、时间、预算、上下文和权限约束，会选择而不是假装全知。
5. **后果**：行动会改变世界，也会留下可追溯、可恢复的痕迹。
6. **关系**：从有来源的共同经历中形成局部、可修订的相处方式，而不是固定人格画像。
7. **节律**：`active`、`waiting`、`watching`、`sleeping`、`blocked` 对应真实状态，而不是装饰动画。

这不意味着声称 Agent 有人类意识或主观感受。Qi 不用虚构情绪值、假装清醒或过度拟人化制造亲密。
诚实的能力边界不会削弱生命感；它让关系建立在真实、连续、可理解的机制上。

## 4. 共处的是同一个世界

聊天记录不是世界本身。Workspace 文件、进程、浏览器状态、外部对象、Goal、Memory、约束、承诺和
Evidence 才组成可行动的现实；对话只是观察和改变这份现实的一条通道。

因此：

- **Session** 保存可重放的共同经历，而不是只保存聊天文本；
- **Goal** 是有完成条件、预算、证据和停止规则的持续承诺，不是普通 todo；
- **Memory** 是有来源、作用域、置信度和遗忘机制的声明，不是对人的永久画像；
- **守望** 让时间与外部变化进入关系，但必须有期限、注意力策略和关闭条件；
- **Web 控制面** 应让人理解 Goal、状态、记忆来源、授权、效果和证据，而不是复制一个聊天窗口。

当前 Web 实现仍是只读的世界观察面。可写、可审批的远程控制面是产品方向，但在单写者、认证、
授权和恢复协议成立之前，不把它包装成已经具备的能力。

## 5. 同行、追寻、守望

产品不以职业或“AI 员工”命名关系，而提供三个面向人的入口：

| 入口 | 关系体验 | 主要运行基础 |
| --- | --- | --- |
| **同行** | 人与 Agent 一起想、一起做，可随时提问、转向或接手 | 用户触发的 Turn |
| **追寻** | 围绕一个 Goal 在预算和完成契约内持续推进 | Goal-based continuation |
| **守望** | 对时间或事件保持感知，在合适条件下记录、提醒、请求关注或行动 | Time/Event watcher |

它们是人理解关系与控制权的产品投影，不是三个互斥的 Kernel 状态。一次真实经历可以从同行形成
Goal，进入追寻，再留下有期限的守望。

当前稳定入口仍以用户触发的**同行**为主。Session-local **追寻**已具备 Goal 合约、Run binding、
`/goal` 控制与证据完成路径，但仍需真实用户验证持续推进与停止体验；**守望**仍以 Scheduler 基础
为主，尚未形成经过验证的完整产品入口。在注意力、通知、停止和恢复体验稳定之前，二者仍是明确的
产品方向，而不是可宣称已交付的模式名称。

## 6. 自治不是一个开关

Qi 把“何时启动、由谁继续”与“允许做什么”分开：

| 激活与延续方式 | 触发 | 必须明确的控制边界 |
| --- | --- | --- |
| **Turn-based** | 用户消息 | 本次交互范围、验收与可用能力 |
| **Goal-based** | Goal 合约 | 成功证据、预算、停止和升级条件 |
| **Time-based** | 时间表 | 时区、频率、静默时段、最长存续和关闭条件 |
| **Proactive** | 外部事件或条件 | 事件范围、注意力策略、并发、分工和外部影响 |

`Ask / Plan / Agent` 描述当前 Session 的交互方式；`Turn / Goal / Time / Proactive` 描述激活与延续；
`同行 / 追寻 / 守望` 描述人感受到的产品关系。三者相互关联，但任何一个标签都不会授予写入、
执行、发布、花费、后台运行或委派权限。

真正的自治来自有边界的主动性：意图可见、授权可撤回、停止条件明确、效果可追踪、完成有证据。

## 7. 产品体验的检验标准

每次重要设计都应回答：

- 用户能否感到一个诚实而连续的 Agent，而不是一次性回答器或角色表演？
- Agent 能否理解正在共同承担的 Goal，并从有来源的 Memory 中恢复上下文？
- 它能否等待和守望，而不把主动性变成通知骚扰？
- 用户能否看懂它为何启动、获得了什么权限、改变了什么、为何停止？
- TUI 与 Web 是否呈现同一个真实世界，而不是各自维护演示状态？
- 当模型犯错、效果未知或用户改变主意时，系统能否拒绝、暂停、恢复和纠正？

“生命感”与“可控”不是两条互相抵消的路线。Qi 的核心产品命题，正是让连续关系、有限自治和人的
最终控制权在同一个世界中同时成立。
